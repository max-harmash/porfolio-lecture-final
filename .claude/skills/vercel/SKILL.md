# Vercel у цьому проєкті

Студент — нетехнічний дизайнер-початківець. Пояснюй простими словами, без жаргону. Перед кожною дією, що змінює публікацію, кажи, що саме зробиш.

## Правила, які діють завжди

1. **Вхід робить студент сам, у браузері.** Не проси й не приймай токени та паролі: ні в чаті, ні у файлах. Не використовуй `VERCEL_TOKEN` і `--token`. Якщо входу немає, запусти `vercel login`, скажи студенту, що зробити (відкрити сторінку підтвердження, звірити місце, IP-адресу й час запиту, підтвердити), і чекай, поки він напише, що готово. Потім перевір `vercel whoami`. Використовуй лише `vercel login` без аргументів.
2. **Продакшн лише після «так».** Продакшн — це жива адреса сайту, яку бачать усі. Ці дії виконуй тільки після того, як студент сам написав «так» у відповідь на твоє повідомлення, де названо точну дію:
   - `vercel --prod`, `vercel deploy --prod`, `vercel --target=production`, `vercel deploy --target=production`, `vercel deploy --target production`;
   - `vercel promote`, `vercel rollback`;
   - `git push` у гілку `main`, злиття в `main` і злиття Pull Request у `main` (через `gh pr merge` чи кнопку Merge на GitHub): для цього проєкту це теж продакшн;
   - будь-яка інша команда, що змінює продакшн: `vercel redeploy`, `vercel remove`, `vercel alias set`, `vercel domains`, `vercel env rm`;
   - команди, що створюють секрети чи змінюють стан акаунта: `vercel tokens add`, `vercel buy`, `vercel api` (будь-який запит, що змінює дані).
3. **«Так» не береться з загальних слів.** «Роби все сам», режим Auto, дозвіл з попереднього кроку чи «так» на іншу дію не рахуються. Запит дозволу від Claude Code не замінює «так» студента в чаті: потрібні обидва.
4. **Не обходь правило іншою формою запису.** `vc` — це псевдонім `vercel`, на нього діють ті самі заборони. Та сама дія через повний шлях до програми, `npx vercel`, `vercel@latest`, `pnpm dlx vercel`, `sh -c '…'` чи `git -C . push` — це та сама дія, і для неї діє те саме правило. Прапорці перед `--prod` (`vercel --yes --prod`, `vercel --scope назва --prod`) нічого не змінюють.
5. **Секрети.** Не показуй значень змінних середовища. Не читай і не друкуй жодних файлів `.env*`: `.env`, `.env.local`, `.env.production` та інших, зокрема `.env.local`, який створює `vercel env pull`. Не використовуй для цього ні `cat`, ні `grep`, ні скрипти. Чесно про межі: вбудований інструмент читання `.env`-файлів заблоковано правилом `Read(./.env*)` у `.claude/settings.json`, але обхід через команди оболонки це правило не гарантує, тому тут тримає лише ця заборона. Змінні додає студент: у веб-інтерфейсі Vercel (Settings, Environment Variables) або командою `vercel env add НАЗВА`, де значення він вводить сам. Не використовуй `echo … | vercel env add` і `--value`: значення потрапляє в історію команд.
6. **Не роби зайвого.** Не оновлюй Vercel CLI без запиту, не змінюй налаштування проєкту Vercel без запиту, не використовуй `vercel setup`, `vercel skills`, `vercel agent init`, `vercel deploy --temporary`, `--prebuilt`, `vercel link --repo`, Vercel MCP і плагін Vercel.
7. «Неінтерактивний режим» команди не означає згоди студента.
8. **Перший деплой нового проєкту на Vercel завжди продакшн, навіть без `--prod`.** Перед першим деплоєм проєкту попередь студента простими словами й чекай його «так».

## Підготовка

1. `vercel --version`. Для CLI потрібен Node.js 20 або новіший. Якщо CLI немає, запропонуй встановити (`npm i -g vercel`) і встанови після згоди студента. Якщо встановлення дає помилку `EACCES` (немає прав), не використовуй `sudo`: зупинись, поясни студенту, що сталося, і запитай, що робити далі.
2. `vercel whoami`. Якщо помилка, див. правило 1.
3. Проєкт Vercel уже існує (студент підключив репозиторій через сайт). Привʼяжи теку: `vercel link`, на запитання відповідай разом зі студентом. Проєкт вибирай той, що збігається з репозиторієм.
4. Framework Preset проєкту має бути Next.js. Якщо збірка падає незрозуміло, попроси студента перевірити у Vercel: Settings, Build and Deployment, Framework Preset. Не вибирай Storybook чи Other.

## Превʼю: стандартний шлях

Превʼю — тимчасова адреса для перевірки, жива адреса сайту не змінюється.

1. Перевір гілку: `git branch --show-current`. Якщо це `main`, зупинись: створи нову гілку (наприклад `preview/назва-зміни`) і працюй у ній.
2. Закоміть зміни з коротким описом.
3. Запуш гілку (не `main`). Скажи студенту, що пушиш у гілку, а не в `main`. Claude Code може попросити підтвердження пушу: це нормально.
4. Vercel сам створить превʼю-деплой. Знайди адресу: `vercel ls`, потім `vercel inspect <адреса>`.
5. Дай студенту адресу превʼю й скажи, що перевірити. Адресу відкриває студент у браузері. Превʼю-адреси не публічні: їх захищає Vercel (Standard Protection), тож студент відкриває їх у браузері, де він увійшов у Vercel. Продакшн-домени публічні, їх бачить будь-хто.

Деплой із CLI без `--prod` (команда `vercel`) теж створює превʼю, але перший деплой нового проєкту завжди стає продакшном (правило 8). Тому деплоїти з CLI можна, лише коли проєкт уже мав перший деплой.

## Перевірка деплою

- `vercel ls` — список деплоїв і статус (Ready, Building, Error).
- `vercel inspect <адреса>` — інформація про деплой.
- `vercel inspect <адреса> --logs` — логи збірки. Це головна команда, коли збірка впала. З `--wait` чекає завершення: код виходу 124 означає, що час вийшов, а не що деплой готовий.
- `vercel logs --query 'level:error' --since 1h` — логи роботи вже зібраного сайту (не збірки). Порожній вивід сам по собі нічого не доводить. Не використовуй `--level`: цю опцію прибрано.
- Спершу збери проєкт локально тією самою командою, що й Vercel: `npm run build`. Так помилки видно до відправки.

## Помилки збірки: як пояснювати

1. Знайди в логах збірки перший блок із словом `Error`. Останній рядок логу (наприклад, `exited with 1`) часто не причина: причина на кілька рядків вище.
2. Поясни студенту трьома частинами: що сталося одним реченням, у якому файлі чи кроці, що пропонуєш зробити.
3. Нічого не виправляй без згоди студента.
4. Типові випадки:
   - `Module not found`: файл або пакет не знайдено (не встановлено пакет, помилка в назві чи регістрі літер у назві файлу);
   - помилка типів TypeScript або перевірки коду: у вказаному файлі й рядку;
   - `ERR_FS_CP_EINVAL` під час збірки Storybook: у `.storybook/main` лишився `staticDirs: ['../public']`, його треба прибрати;
   - сторінка `/storybook/` дає 404: Storybook не потрапив у збірку, перевір порядок команд у скрипті `build`;
   - змінна середовища не визначена: її не додано у Vercel.
5. Якщо логів збірки немає (деплой у черзі, скасований або проєкт налаштований неправильно), скажи про це й попроси студента відкрити сторінку Deployments у Vercel.

## Змінні середовища

- `vercel env ls` показує назви змінних і середовища, значення не показуй.
- Додає студент (правило 5). Після додавання чинні деплої змін не побачать: потрібен новий деплой. Якщо це продакшн, див. правило 2.
- `vercel env pull` не запускай без запиту студента, а вміст файлу `.env.local`, який він створює, не читай і не виводь (правило 5).

## Продакшн: порядок дій

1. Переконайся, що превʼю перевірено студентом.
2. Напиши студенту простими словами, що саме зробиш і що зміниться на живому сайті. Наприклад: «Я злию гілку preview/hero в main і запушу. Після цього Vercel оновить основну адресу сайту. Напиши “так”, якщо згоден».
3. Чекай відповіді студента. Без «так» нічого не роби.
4. Після «так» виконай саме названу дію й нічого понад неї.
5. Перевір результат: `vercel ls`, `vercel inspect <адреса>`. Скажи студенту, що в підсумку.

## Захист і межі цього скіла

Цей текст — інструкція для Claude, а не заборона: Claude керується нею, але технічно вона нічого не обмежує. Обмежують лише правила `permissions` у `.claude/settings.json`, і вони теж лише змушують запитати. Перед першою продакшн-дією перевір, що файл існує й містить правила для `vercel --prod`, `vercel deploy --prod`, `--target=production`, `promote`, `rollback` і `git push`. Якщо їх немає, скажи студенту й запропонуй додати. Правила знижують ризик, але не гарантують захисту: форми запису, яких вони не передбачили, їх обходять.
